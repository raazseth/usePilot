# ADR-023: Cryptographic Execution Manifest

## Context
When an execution run completes, auditing, verification, and debugging require a complete, tamper-evident record of what was planned, what was configured, which adapters performed work, and what the final outcome was. Relying solely on raw journal entries makes forensic verification and reproducibility cumbersome.

## Decision
Introduce the **Execution Manifest** (`ExecutionManifest`) generated by `ManifestGenerator`:
1. Every execution run produces an immutable, cryptographic execution manifest upon completion.
2. The manifest records:
   - `runId` and blueprint identity (`blueprintId`, `blueprintHash`)
   - Complete execution outcome (`status`, `completedTasks`, `failedTasks`, `totalTasks`, `durationMs`)
   - Applied execution policy (`ExecutionPolicy`)
   - Inventory of selected adapters (`SelectedAdapterRecord[]`) including capability ID, adapter ID, sandbox status, tasks executed, error count, and recovery count
   - Runtime environment metadata (Node/Bun version, platform, architecture)
   - Final SHA-256 content digest computed over canonical normalized payload.
3. The manifest is persisted in SQLite (`execution_manifests` table) and retrievable via `ExecutionService`.

## Consequences
- Produces a tamper-evident, deterministic receipt for every execution.
- Enables offline verification, replay audits, and forensic analysis of adapter behavior.
- Serves as the authoritative source of truth for execution reporting and historical metrics.
