# Execution Subsystem Documentation

This directory contains the complete technical specification for the usePilot Execution Subsystem (`@usepilot/execution-core` and `@usepilot/execution-types`).

---

## 1. What is this?

The Execution Subsystem is a deterministic runtime engine that consumes sealed `ExecutionBlueprint`s generated by the Planner and orchestrates task execution across capability adapters (browser, filesystem, desktop, vision) without prompting an LLM during the execution loop.

It manages state machine transitions, task scheduling, policy-based capability negotiation, sandboxed execution, independent postcondition verification, exponential backoff retries, human approval gates, session pooling, append-only SQLite journaling, and tamper-evident cryptographic manifests.

---

## 2. Why does it exist?

Standard AI agents rely on recursive LLM loops to decide what tool to run next. This approach has critical flaws:
- Execution paths are unpredictable and non-reproducible.
- Failures cannot be safely recovered without risking hallucinations.
- Retries and resource allocation cannot be strictly constrained by time or memory bounds.

usePilot's Execution Subsystem operates strictly on pre-computed blueprints:
- **Zero In-Loop LLM Calls**: Tasks execute via native adapters based on deterministic DAG topological batches.
- **Strict Verification**: Every task result is verified against postcondition assertions before proceeding.
- **Fail-Safe Self-Healing**: Failed locators cascade through algorithmic heuristics (`dom → semantic → visual → ocr`), bypassing broken selectors in under 200ms.
- **Cryptographic Auditability**: Every state mutation is logged to an append-only SQLite journal and sealed with a SHA-256 execution manifest.
