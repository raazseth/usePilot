# Execution Engine Overview

The Execution Engine (`@usepilot/execution-core`) executes immutable `ExecutionBlueprint`s generated by the Cognitive Planner. It resolves abstract capabilities to concrete sandboxed adapters, enforces approval policies, verifies environmental state changes independently, and generates tamper-evident audit receipts with zero language model prompting in the execution loop.

---

## Core Subsystem Primitives

### 1. Execution Runner (`ExecutionRunner`)
Coordinates the end-to-end task execution lifecycle. It advances tasks through the `ExecutionStateMachine` (`idle -> initializing -> planning -> running -> paused -> recovering -> completed / failed / aborted`), evaluates policies, and handles abort signals.

### 2. Capability Registry & Immutable Manifests
Adapters declare an immutable `AdapterManifest`:
```typescript
export interface AdapterManifest {
  readonly id: string
  readonly name: string
  readonly version: string
  readonly apiVersion: string
  readonly runtimeVersion: string
  readonly capabilities: readonly TaskCapability[]
  readonly dependencies: readonly CapabilityDependencyRequirement[]
}
```
The registry resolves capabilities to concrete adapters via `PolicyBasedCapabilityNegotiator`, matching runtime availability and OS platform without hardcoded bindings.

### 3. Capability Dependency Graph
Maps each capability to its required, optional, and fallback subsystem dependencies and permissions:
- `required`: Subsystem must be initialized and available (e.g. `browser` for `navigate_website`).
- `optional`: Subsystem provides progressive enhancement (e.g. `vision` for visual locators).
- `fallback`: Subsystem used if preferred capability path is unavailable.

### 4. Runtime Correlation Chain
Ties every execution entity to an immutable correlation context:
```typescript
export interface RuntimeCorrelationChain {
  runId: string
  traceId: string
  taskId?: string | undefined
  observationId?: string | undefined
  verificationId?: string | undefined
  replayStepId?: string | undefined
  manifestId?: string | undefined
}
```

### 5. Execution Timeline
An ordered sequence of reference entries linking lifecycle occurrences without payload duplication:
```typescript
export interface ExecutionTimelineEntry {
  readonly sequence: number
  readonly timestamp: number
  readonly type: TimelineEventType
  readonly runId: string
  readonly summary: string
  readonly taskId?: string | undefined
  readonly journalEntryId?: string | undefined
  readonly observationId?: string | undefined
  readonly verificationId?: string | undefined
  readonly checkpointId?: string | undefined
  readonly replayStepId?: string | undefined
}
```

### 6. Independent Verification & Self-Healing
Task completion requires physical state proof via `VerificationEngine`. If a locator fails during execution, `SelfHealingPipeline` resolves the target through a 4-stage local cascade (`dom -> semantic -> visual -> ocr`) before failing.

### 7. Failure Bundle (`FailureBundleGenerator`)
When an execution fails, `FailureBundleGenerator` bundles the failure manifest, execution report, journal entries, verification failures, and disk artifacts into `failure-bundle/failure-manifest.json` for post-mortem forensics.

### 8. Execution Manifest (`ExecutionManifest`)
A cryptographic receipt containing execution metadata, adapter run statistics, and a final SHA-256 content digest stored in SQLite upon completion.
